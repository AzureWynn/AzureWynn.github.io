从 GPIO 到 MQTT：一次 ESP32-S3 网络与 IoT 功能实践

November 27, 2026
ESP32-S3 IoT MQTT 嵌入式 Wi-Fi FreeRTOS

TL;DR (English)

I built a complete IoT data pipeline around the ESP32-S3-DevKitC-1 (N16R8): sensor sampling → device networking → on-device web UI → MQTT telemetry → a Go backend service. It is not four separate demos — it is one combined firmware running six FreeRTOS tasks across both cores, plus a Go service that subscribes to the device in real time.

Temperature Sensor ──▶ ESP32-S3 ──▶ MQTT Broker ──▶ Backend Service
   DHT11 reads temp    collects data & builds MQTT messages   publishes & routes   subscribes & receives

Highlights:

  • Self-implemented protocols: DHT11 single-bus timing (bit-level read + checksum) and a full MQTT 3.1.1 client on raw WiFiClient — no PubSubClient.
  • NAPT traffic forwarding: the official SDK lacks NAPT, so I rebuilt the esp32-arduino SDK via esp32-arduino-lib-builder to enable CONFIG_LWIP_NAPT.
  • Wi-Fi provisioning: AP-mode setup page + SmartConfig, with configuration persisted in SPIFFS.
  • Two-way MQTT: QoS1 status telemetry (temp/humidity/Wi-Fi/heap) every 10s + a command channel (led:*, ping, restart) for instant control.
  • Go backend: layered service — MQTT subscriber, JSONL persistence, web/SSE console, and command publishing.

1. 为什么开始接触 ESP32-S3

我的日常工作在云端：云商业平台的后端服务，通过 HTTPS API 与 POS、自助终端等设备端系统集成。设备那头的世界对我来说一直是一个「接口之后」的黑盒——串口、GPIO、固件、单总线协议，这些词在接口文档里出现过，但我没有亲手碰过。

参加 MachineCat 黑客松时，机器人硬件是队友带来的现成套件，我负责软件栈，通过它暴露的 HTTP / WebSocket / Bluetooth 接口去驱动。这让我意识到：我擅长接口之上的部分，但对接口之下的部分缺乏第一手体感。

所以这次实验的目的很明确：

  1. 补齐设备侧的体感：亲手做 GPIO、传感器时序、Wi-Fi 配网这些「接口之下」的事；
  2. 验证完整链路：不是单个点灯 Demo，而是从传感器到后端服务的一条完整数据通路；
  3. 反哺云端工作：理解设备端的约束（阻塞、内存、时序）之后，再设计设备对接 API 时会更有判断。

我的目标不是转型嵌入式工程师，而是把「IoT 云端服务」这一层经验补上设备侧的另一半视角。

仓库分三个入口：

  • server/：Go 后端，通过 MQTT Broker 与设备通信并提供 Web 控制台

3. GPIO：呼吸灯和触摸唤醒

这是最外层的「hello world」，但我没有停在点灯。

WS2812 呼吸灯：GPIO48 上驱动一颗 WS2812（GRB 时序），做了 breath / solid / off 三态状态机——呼吸模式按周期插值亮度，固定色直接设置，熄灭清零。状态切换可以来自网页、MQTT 命令、触摸或串口，全部收敛到同一个状态机，避免多入口互相覆盖。

电容触摸：GPIO4（TOUCH4）实现触摸触发 LED 状态切换。自己写了完整检测逻辑：

  • 基线校准：上电时采样若干次取基线，适配不同环境下的电容本底；
  • 阈值判断：读数偏离基线超过阈值判定为「按下」；
  • 去抖 + 边沿检测：只有「释放→按下」的下降沿才算一次有效触发，避免长按被识别成连续多次。

DHT11 温湿度：这是 GPIO 层最有价值的部分。没有引入第三方 DHT 库，自己实现了单总线时序：主机拉低起始信号 → 等待传感器响应 → 逐位读取 40 bit（湿度 16 + 温度 16 + 校验和 8）→ 校验和验证。做的时候对「传感器数据的每一位都是靠微秒级延时数出来的」这件事有了非常具体的体感——这正是云端视角里永远看不到的部分。

4. Wi-Fi：扫描、配置和 AP 模式

Wi-Fi 层实现了完整的生命周期管理：

  • STA 连接：配置保存在 SPIFFS 的 /wifi.json，重启后自动按已存配置连接；
  • 扫描：WiFi.scanNetworks() 是阻塞操作（1~3 秒），我把它收敛到驱动层：scanBegin() 加锁扫描并缓存结果，网页和串口命令都读缓存，阻塞只影响调用方自己的任务；
  • AP 配网模式：没有已存配置时自动开启热点 ESP32-W，提供 http://192.168.4.1 配网页面——扫描列表选网、输密码、保存连接，成功后自动跳到 LED 控制页；
  • SmartConfig（ESP-Touch）：配网页、串口命令和 HTTP API 三个入口都能触发，手机 App 广播配网（必须在 2.4G 频段），60 秒超时自动回退 AP 模式。

这个阶段的收获是：「配网」不是一个功能，而是一套状态机——已存配置 / 内置回退 / AP 模式 / SmartConfig 进行中，各种状态之间的转换和超时回退比连接本身更费心思。

5. NAPT：设备网络转发实践

NAPT 是这个实验最初的动机：让设备接入 Wi-Fi 后，把自己开的 AP 热点下面的下游设备的流量做网络地址转换，转发到上行网络——一个透明代理 / 流量转发节点。

踩的坑也最多，因为官方 SDK 不带 NAPT：

  1. PlatformIO 自带的 Arduino 核心 2.0.17 对应 ESP-IDF 4.4.7，其预编译 SDK 没有 CONFIG_LWIP_NAPT；
  2. 只能用 Espressif 官方的 esp32-arduino-lib-builder，在 release/v4.4 分支上本地重新编译一份带 NAPT 的 SDK；
  3. 编译时打开 CONFIG_LWIP_NAPT=y，产物按 PlatformIO 期望的 tools/sdk/ 结构替换进去。

最后在板上验证通过：设备 STA 连接上行 Wi-Fi，AP 热点下游设备把设备当网关，流量经 NAPT 转发出去。启动日志里 [napt] enabled on AP 就是这条链路活着的证据。

这次「为了一个编译开关重编整个 SDK」的经历，让我对「SDK 里每个能力都是被编译选项裁剪出来的」有了具体的认识——这也解释了为什么不同厂商设备的 API 能力差异那么大。

6. Web Server：设备配置入口

设备内置 HTTP 服务（端口 80），同时服务 AP 和局域网两个接口：

场景访问 / 看到的
未连接 Wi-Fi配网页（扫描选网 + SmartConfig 入口）
已连接LED 控制页 + Wi-Fi 设置面板（状态/SSID/信号/IP，可改配、清除配置回配网模式）

主要 API：

GET  /api/wifi             Wi-Fi 状态（state/ssid/ip/rssi/...）
POST /api/wifi             保存配置并连接
GET  /api/wifi/scan        扫描网络（读驱动缓存）
POST /api/wifi/smartconfig 启动 ESP-Touch 监听
POST /api/wifi/reset       清除配置，回到 AP 配网模式
POST /api/led              LED 控制

作为平时写后端 API 的人，做这个嵌入式 Web 服务最大的不同是资源约束：不能随手开连接池、不能无脑加缓存，阻塞操作（扫描、MQTT 读写）必须想清楚跑在哪个任务里、会不会把别的接口饿死。

7. MQTT：温度传感器数据上报

这是整个实验的重点：一条从传感器到后端的完整数据链路。

7.1 自实现 MQTT 3.1.1 客户端

设备端没有用 PubSubClient，而是直接基于 WiFiClient 实现了 MQTT 3.1.1 协议：CONNECT / SUBSCRIBE / PUBLISH 报文的组包与解析、QoS0/1、keepalive、断线自动重连。做协议层的目的很功利——想知道「MQTT 客户端库」这层抽象下面到底是什么，以及连接管理、重连退避这些工程细节在资源受限设备上怎么处理。

7.2 数据链路

Temperature Sensor ──▶ ESP32-S3 ──▶ MQTT Broker ──▶ Backend Service
   DHT11 读取温度       采集并组织 MQTT 消息   发布与接收       订阅并接收温度数据
  • Temperature Sensor：DHT11 在独立任务里每 2 秒采样一次温湿度并缓存；
  • ESP32-S3：每 10 秒把传感器数据 + Wi-Fi 状态 + LED 状态 + 堆内存组织成 JSON，发布到 esp32/device/status（QoS1）；LED 状态变化时还会即时上报，不只是周期心跳；
  • MQTT Broker：EMQX 监听 1883，负责消息路由；真实地址和凭据不进仓库；
  • Backend Service：Go 服务订阅 esp32/device/status，把状态与温度数据写 JSONL 落盘，并通过 Web / SSE 实时展示。

上报消息长这样：

{"wifi":"connected","ssid":"<WIFI_SSID>","ip":"<DEVICE_IP>","rssi":-56,
 "uptime":110,"heap":281384,"led_mode":"solid","led_color":"ff0000",
 "led_bright":100,"led_speed":1,"temperature":26,"humidity":60}

7.3 命令下发（反向链路）

反向链路同样可用：Go 服务 / mosquitto_pub 向 esp32/device/cmd（QoS1）发布纯文本命令，设备执行后即时回报状态：

mosquitto_pub -h <BROKER_HOST> -t 'esp32/device/cmd' -m 'led:color:00ff00'
mosquitto_pub -h <BROKER_HOST> -t 'esp32/device/cmd' -m 'ping'   # 设备回 {"pong":1}

支持 led:on/off/color/bright/breath/speed、wifi:status、ping、restart。这条「云端发指令 → 设备执行 → 状态即时回传」的闭环，和我日常工作里设备对接业务的模型完全同构——只不过这次两端都是我亲手写的。

7.4 Go 后端服务

server/ 按分层结构写：config 读 YAML、infrastructure/mqttclient 连 Broker、adapter 做消息转换、application 管状态流、interfaces/http 提供 Web 页面和 API。Web 控制台默认 18081 端口，可以实时看到设备状态和温度曲线，也能反向下发命令。

7.5 组合运行：FreeRTOS 多任务

所有功能不是串在 loop() 里的，而是 6 个 FreeRTOS 任务按双核分工：

任务核心周期职责
wifiTask010msWi-Fi 驱动、配网轮询、状态事件
mqttTask010msMQTT 收发、状态上报、命令处理
webTask05msHTTP 请求处理
ledTask120msLED 状态机、触摸采样
consoleTask15ms串口命令
dhtTask12sDHT11 采样并缓存

任务间通过队列式事件总线解耦：webTask 下发 LED 命令只入队，MQTT 上报由 mqttTask 在自己的上下文完成，避免跨任务 I/O；共享资源（SPIFFS、Wi-Fi 驱动、MQTT 客户端、配网状态）全部加互斥锁，锁顺序固定防止死锁。

代码组织上用了接口注入（ILedDriver / IWifiDriver / IMqttClient / IFileSystem / IConsole）、Pimpl 隐藏第三方库、工厂统一创建驱动——本质上是把我在后端积累的分层习惯搬到了固件里。

8. 遇到的问题和解决过程

完整的踩坑记录在仓库 doc/04-踩坑记录.md 里，挑五个代表性的：

① 选错 SDK 分支，白构建了一份 IDF 5.3 SDK 现象：花大量时间构建出 5.3 的 SDK，但固件根本用不上。 原因：espressif32 平台包号 3.20017.241212 开头的 3 是 PlatformIO 框架 major 版本，20017 才是 Arduino 核心 2.0.17，实际对应 IDF 4.4.7。 解决：确认版本矩阵后用 release/v4.4 分支重新构建。教训：工具链版本号要先读文档确认语义，不要按直觉猜。

② 代理与镜像导致构建环境不可用 现象：git clone / curl / pip 全部卡死，pip 卡在 “Fetching project description” 不动。 原因：本机代理环境变量对 GitHub / dl.espressif / PyPI 不生效；pypi.org 在当前网络不可达。 解决：构建前 unset http_proxy https_proxy ...；pip 换 PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/。教训：构建脚本长时间挂起时，不要用管道看输出，落盘到日志文件再查。

③ 大仓库 clone 反复断流 现象：esp-idf（>2GB）、arduino-esp32（>1GB）等仓库反复 early EOF。 解决：浅克隆 --depth 1 -b <branch>；固定 commit 用 git fetch --depth 1 origin <sha>；实在不行用 codeload tarball 走 HTTP。esp_wifi/lib、esp_phy/lib 两个 100MB+ 的预编译 blob 子模块是重灾区，手动下载解压绕过。

④ 官方 SDK 没有 NAPT 现象：代码调用 NAPT 相关能力编译不过。 原因：Arduino Core 2.0.17 配套的预编译 SDK 未开启 CONFIG_LWIP_NAPT。 解决：esp32-arduino-lib-builder（release/v4.4）本地重编带 NAPT 的 SDK，按 PlatformIO 期望的产物结构替换。注意 lib-builder 的产物和 pio 官方平台的 builder 脚本不通用，不能整目录乱覆盖。

⑤ SPIFFS 配置”改了不生效” 现象：改了 data/mqtt.json 的 Broker 地址，设备还是连旧地址。 原因：配置文件烧在 SPIFFS 分区，只执行编译烧录固件不会更新它。 解决：改配置后必须 pio run -t uploadfs。教训：分区表里不同区域的数据有不同的更新路径，这和云端「改配置要区分热更新还是重新部署」是同一类问题。

后续计划（按优先级）：

  1. MQTT over TLS：目前是 TCP 明文 + 可选凭据，下一步换 8883 端口做证书校验——这正好能复用我做 Webhook 验签时的证书链知识；
  2. OTA 升级：固件远程更新，配合 MQTT 命令通道做成「服务端推送版本 → 设备分批升级」的模型；
  3. 传感器扩展：DHT11 精度有限，换 SHT3x（I²C）对比两种总线协议的实现差异；
  4. 更底层的 IDF 练习：idf/ 工程继续深入 RMT、中断、双核调度，而不是停留在 Arduino 封装层；
  5. 云端反哺：把设备端学到的约束（内存、阻塞、弱网）沉淀成设备对接 API 设计 checklist。

这次实验最直接的价值，是让我在「云后端 ↔ 设备集成」这条自己最熟悉的职业主线上，第一次同时握住了两端。
