DDD Discovery & TDD Delivery Workflows

Two self-authored engineering workflow skills: strategic DDD → SDD → BDD requirement discovery, and tactical DDD → spec-to-test → TDD delivery with dependency injection and review gates.

Published October 1, 2026
DDD TDD BDD Methodology AI Workflow

What they are

Two reusable, self-authored workflow skills that define how I take a product idea from discovery to delivered code:

  1. DDD Product Discovery (upstream) — strategic DDD: bounded contexts, ubiquitous language, context mapping → SDD interface specifications → BDD acceptance scenarios → product planning.
  2. DDD/TDD Expert Team (downstream) — tactical DDD modeling → specification-to-test derivation → TDD (Red / Green / Refactor) → layered implementation with dependency injection → multi-role review gates.

Why I built them

AI-assisted coding makes implementation fast — but speed without discipline produces mush. These workflows make the boundaries explicit before any code is generated:

  • Requirements become bounded contexts and ubiquitous language, not a pile of tickets.
  • Interfaces become specifications; specifications become acceptance scenarios.
  • Scenarios become tests; tests drive implementation through Red / Green / Refactor.
  • Review gates check layering and dependency direction, so AI-generated code lands in the right place with the right seams.

How I use them

They are my daily working process, not documentation for show. AI agents accelerate each step — drafting specs, generating tests, implementing against them — while the boundary decisions stay mine. The result is AI-assisted delivery that doesn’t sacrifice architectural discipline: fast output, reviewable structure, and tests that exist because the spec demanded them.

What it demonstrates

  • Specification-first engineering habit, applied end-to-end.
  • Ability to design reusable engineering processes — not just write code.
  • A concrete answer to “how do you keep quality when using AI?”
